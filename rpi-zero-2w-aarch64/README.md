## Build and run

```bash
cd tests
./run.sh build -c aarch64-rpi-zero-2w-cmake-gcc-debug

./run.sh -c aarch64-rpi-zero-2w-cmake-gcc-debug           # build + the selected tests
./run.sh list                        # the CTest cases
./run.sh --hwd                       # include the board cases
```

`run.sh` configures and builds first, then runs CTest. It takes an
application directory name (`mtp-example`), a full CTest name or a
selection id; without a name it runs the selected tests. Hardware
(`-hwd`) cases need the board and the probe: `--hwd` includes them,
`all` runs everything.

The results are files too: `build/<configuration>/ctest.xml` (JUnit;
CTest caps each console snippet at 1 KiB),
`build/<configuration>/ctest.log` (the full CTest output), and the complete
µTest++ TAP report next to each runner log (`<app>.tap` in `.hw-logs`,
`.qemu-logs` or `.host-logs`).

## Adding new functionality to this workspace

Everything is compiled from source: the kernel (`micro-os-plus-iii-smp/`) and the port
(`micro-os-plus-iii-aarch64/`) export CMake INTERFACE targets, and the test executable compiles
their sources together with its own. There is no library to rebuild or install;
after any change run `./run.sh` (it builds first).

### Which file picks up what

| You add | Put it in | Picked up by | Edit a CMake file? |
| --- | --- | --- | --- |
| `.cpp` of the test | `micro-os-plus-iii-aarch64/test/rpi-zero-2w/smp-mat-test/` | `test/CMakeLists.txt` globs `<app>/*.cpp` | no |
| header of the test | the same directory | the directory is on the include path | no |
| `.c` / `.S` of the test | the same directory | not globbed | `board_test_sources()` in `test/rpi-zero-2w/tests.cmake` |
| code shared by all tests of the board | `micro-os-plus-iii-aarch64/test/rpi-zero-2w/src/*.cpp`, `include/` | globbed, on the include path | no |
| board code (driver, start-up) | `micro-os-plus-iii-aarch64/test/boards/rpi-zero-2w/src/` | `micro-os-plus-iii-aarch64/CMakeLists.txt` globs `*.cpp`, `*.S` | no |
| board glue used by some tests only | `micro-os-plus-iii-aarch64/test/boards/rpi-zero-2w/glue/` | named, never globbed | `board.cmake` variable + `board_test_sources()` |
| port source | `micro-os-plus-iii-aarch64/src/` | explicit list | `target_sources (micro-os-plus-iii-aarch64-interface ...)` in `micro-os-plus-iii-aarch64/CMakeLists.txt` |
| kernel source | `micro-os-plus-iii-smp/src/` | explicit list | `target_sources (micro-os-plus-iii-interface ...)` in `micro-os-plus-iii-smp/CMakeLists.txt` |
| a library | anywhere in the workspace | an INTERFACE or STATIC target | `board_test_libs()` in `tests.cmake` |
| a new test | `micro-os-plus-iii-aarch64/test/rpi-zero-2w/<name>/` | globbed: one executable and one CTest case per directory | only for non-default settings |

The globs use `CONFIGURE_DEPENDS`, and `./run.sh` re-runs CMake every time, so
a new file or directory is noticed without removing the build tree.

### 2. Per-test build settings

`micro-os-plus-iii-aarch64/test/rpi-zero-2w/tests.cmake` is included by `micro-os-plus-iii-aarch64/test/CMakeLists.txt`
and holds everything a directory listing cannot express. Each hook receives the
test name in `_app` and returns a list in `_out`:

| Hook or list | Purpose |
| --- | --- |
| `board_test_defines (_app _out)` | extra compile definitions |
| `board_test_sources (_app _out)` | extra source files (`.c`, `.S`, board glue, files outside the test directory) |
| `board_test_includes (_app _out)` | extra include directories |
| `board_test_linker (_app _out)` | another linker script for the hardware image |
| `board_test_options (_app _out)` | extra compile options for the test's own sources |
| `board_test_ncpu (_app _out)` | `OS_NCPU` for the test (default: the board's `UOS_BOARD_NCPU`) |
| `board_test_libs (_app _out)` | libraries to link |
| `BOARD_TEST_NEED_DEVICES` | tests that link the board device drivers |
| `BOARD_TEST_SELF_CONTAINED` | tests that must not get the shared `test/rpi-zero-2w/src/` |
| `BOARD_TEST_NO_KERNEL` | bare-metal tests, linked without the RTOS |

This board's `tests.cmake` already defines `board_test_defines()`, `board_test_libs()`: add a branch for your test **inside** the existing function. A hook that is not listed here can be added as a new function; the defaults return an empty list.

Example, a definition and an option for one test:

```cmake
function (board_test_defines _app _out)
  if (_app STREQUAL "smp-mat-test")
    set (${_out} MATRIX_SIZE=64 USE_FAST_PATH PARENT_SCOPE)
  else ()
    set (${_out} "" PARENT_SCOPE)
  endif ()
endfunction ()
```

### 3. Add a library

**A library of your own sources.** Keep it inside the workspace, declare it
once in `tests.cmake`, and return it from `board_test_libs()`:

```cmake
# micro-os-plus-iii-aarch64/test/rpi-zero-2w/tests.cmake
if (NOT TARGET mylib)
  add_library (mylib INTERFACE)
  target_sources (mylib INTERFACE
    "${CMAKE_CURRENT_LIST_DIR}/../../libs/mylib/src/mylib.cpp")
  target_include_directories (mylib INTERFACE
    "${CMAKE_CURRENT_LIST_DIR}/../../libs/mylib/include")
  target_compile_definitions (mylib INTERFACE MYLIB_STATIC)
endif ()

function (board_test_libs _app _out)
  if (_app STREQUAL "smp-mat-test")
    set (${_out} mylib PARENT_SCOPE)
  else ()
    set (${_out} "" PARENT_SCOPE)
  endif ()
endfunction ()
```

An INTERFACE library is compiled with the test's own flags (CPU, FPU,
`OS_NCPU`), which is what a bare-metal image needs. `micro-os-plus-iii-aarch64/libs/mylib/` is
only a suggested place; any path works.

**A pre-built archive.** Return its absolute path, and add its headers with
`board_test_includes()`. It must be built with the board's flags
(`-mcpu=cortex-a53`):

```cmake
set (${_out} "${CMAKE_CURRENT_LIST_DIR}/../../libs/vendor/libvendor.a" PARENT_SCOPE)
```

**An optional kernel component.** The kernel exports, besides
`micro-os-plus::iii`, the targets `micro-os-plus::iii-posix-io`, `micro-os-plus::iii-drivers`, `micro-os-plus::iii-startup`, `micro-os-plus::iii-newlib-reent`, `micro-os-plus::iii-semihosting`, `micro-os-plus::iii-trace-itm`, `micro-os-plus::iii-trace-semihosting`, `micro-os-plus::iii-trace-segger-rtt`. Return the one you need
from `board_test_libs()`; the test already links `micro-os-plus::aarch64`.

**A portable harness suite or an xPack.** The selected test uses none, so `tests/sources/` and the xPack libraries were not copied. To use one, copy `tests/sources/<suite>/` (and the xPack under `tests/xpacks/`) from the source harness, list the directory in `tests/platforms/aarch64-rpi-zero-2w/cmake/dependencies-folders.cmake` and return `test::<suite>` from `board_test_libs()`, or re-scaffold selecting a test that already uses it.

### The runtime rule

A board gets µTest++ only if it meets the rule every µTest++ board must meet. The
scaffolder checked it in the sources (`scaffold.json`, `microTestPlus.boards[].runtime`):

- the boot code runs the static constructors (`__libc_init_array` or `os_run_init_array`);
- the linker script keeps `.init_array` between `__init_array_start` and `__init_array_end`;
- the linker script defines the heap, `_Heap_Begin` .. `_Heap_Limit`;
- the start-up hands the heap to the µOS++ free store (`os_startup_initialize_free_store`), which
  `malloc` and `new` use, before the constructors run;
- `sbrk ()` works over the same region.

The starter test checks the same on the target, in its suite "01 - Runtime".

`aarch64-rpi-zero-2w`:

- ok: linker script: .init_array kept, with __init_array_start/__init_array_end (micro-os-plus-iii-aarch64/test/boards/rpi-zero-2w/linker.ld)
- ok: linker script: heap region _Heap_Begin .. _Heap_Limit (micro-os-plus-iii-aarch64/test/boards/rpi-zero-2w/linker.ld)
- ok: boot code runs the static constructors (micro-os-plus-iii-aarch64/test/boards/rpi-zero-2w/src/startup.S)
- ok: the heap is given to the µOS++ free store (malloc) at start-up (micro-os-plus-iii-smp/src/startup/initialise-free-store.cpp)
- ok: sbrk () over _Heap_Begin .. _Heap_Limit (micro-os-plus-iii-smp/src/libc/_sbrk.c)

### The arguments test, `mtp-args`

It checks the transport itself: the runner passes

```text
arm semihosting_cmdline mtp-args --output-file <path>
```

(QEMU: `-semihosting-config ...,arg=mtp-args,arg=--output-file,arg=<path>`;
host: the same two process arguments). The suite checks that `os_main ()`
received at least three words, that `argv[0]` names the test, that
`argv[1]` is `--output-file`, that `argv[2]` ends in `.tap`, and that
`mtp_board::argument_count()` parsed the same count. A runner that drops
the command line fails this CTest case instead of silently running the
test with an empty `argv`.

### The SMP test, `mtp-smp`

On the boards whose other cores the board support can start, `mtp-smp` checks the SMP
scheduler on every core (it is written for `OS_NCPU` cores):

| Suite | What it checks |
| --- | --- |
| 00 Cores | the other cores started and joined the scheduler |
| 01 Affinity | a pinned thread runs on its core; affinity changes at run time |
| 02 Critical sections | `interrupts::critical_section` excludes every core, masks, nests and restores; a core waits while another holds the kernel lock; `scheduler::critical_section` holds off switches on its core and leaves the others running |
| 03 Spinlocks | `mtp_board::spinlock`: no lost update from every core; `try_lock` refused while another core holds it |
| 04 Mutexes | contention from every core; `try_lock`/`timed_lock` against another core; recursive; priority inheritance across cores |
| 05 Scheduler | preemption of a busy thread; `yield` between equal priorities; `sleep_for` on every core; load spread |
| 06 Cross-core sync | semaphore ping-pong, ordered message queue, event flags, a barrier of all cores |
| 07 Queue stress | one producer per core into one bounded queue: nothing lost or duplicated |
| 08 Atomic read-modify-write | `mtp_board::atomic_add ()` from every core; `std::atomic` where the hardware supports it |
| 09 Speed-up | the same CPU-bound work on one core, then on every core at once: at least 0.8 x `OS_NCPU` faster on the board (reported only under QEMU) |

Spinlocks and `atomic_add ()` go through the board's own method, printed at the start of the
report (`# cross-core sync method: ...`):

- Raspberry Pi (AArch64): the exclusive monitor, `LDAXR`/`STLXR`, compiled inline
  (`no-outline-atomics`, not libgcc's run-time choice);
- AArch32: `LDREX`/`STREX` (`LDAEX`/`STLEX` on an ARMv8 core);
- RP2040/RP2350: the SIO hardware spinlocks (8..30 for `spinlock`, 31 for `atomic_add ()`;
  0 is the kernel's, 1 the console's). Their `LDREX`/`STREX` exclude only the same core
  (measured on a Pico 2: 51547 of 100000 increments from two cores survived), so
  `std::atomic` read-modify-write is not checked there and must not be shared between cores.

Inside `scheduler::critical_section` a test must not wait on `sysclock`: on the RP2350 the
scheduler lock masks this core's interrupts and the clock stands still. Bound such waits by
iterations.

### How it works

1. **Registration.** `mtp-example/` is a test directory like the others: the port's
   builder globs it, makes its images, and the platform registers
   `aarch64-rpi-zero-2w-mtp-example-<variant>` with CTest.
2. **Linking.** The µTest++ block in `tests.cmake` declares the INTERFACE library
   `uos-micro-test-plus`: the framework's sources, `mtp_board.cpp`, the include paths, and
   `MICRO_OS_PLUS_MICRO_TEST_PLUS_ENABLED`, `_GNU_SOURCE` and the `MTP_*` defines. The library
   hook links it to every test whose name starts with `mtp-`.
3. **Start-up.** The board boots as for every test: the boot code clears `.bss`, sets up the
   heap, runs the static constructors (the µTest++ runner is one), then calls `os_main ()`
   on the main thread. On the boards whose tests carry their own start-up, `mtp_startup.hpp`
   provides it.
4. **The run.** `os_main ()` calls `mtp_board::start ()`, which routes stdout (below),
   optionally `release_cores ()`, then `mtp_board::run (argc, argv)`: it initialises
   the runner, runs the static suites, prints the RESULT line and ends the run.
   Each suite registers itself with a namespace-scope `mt::static_suite`; there is no
   list of suites to maintain.
5. **The report.** µTest++ prints through stdout. Console model 1: stdout is replaced by a
   stream that writes to the UART at once and sends the text to the host with semihosting
   `SYS_WRITE0`, at the end of each suite (every line under QEMU), because every
   semihosting call halts the cores. Model 2: a strong `_write ()` does the same in place
   of the port's weak stub. Model 3: the host's stdout. The runner (`run-hw.sh`,
   `run-qemu.sh`, `run-host.sh`) collects that output and looks for `RESULT: PASS`.
6. **newlib-nano** (`MTP_NANO_PRINTF=1`). µTest++ prints sizes with `%zu`, which nano does
   not know; the board support wraps the printf family (`-Wl,--wrap=...`) to drop the `z`
   (`size_t` is `unsigned int` there) and links `_printf_float` for the `approx ()` messages.
   The framework stays unchanged.
7. **Boards whose QEMU image replaces the board** (`board_test_qemu_libs` in `tests.cmake`,
   as on the Pico 2): the `mtp-*` tests are hardware only, because the runtime rule was
   checked on the board, not on the emulated stand-in.

### Adding a µTest++ test

Copy the starter test and edit it; no CMake file needs changing:

```bash
cp -r micro-os-plus-iii-aarch64/test/rpi-zero-2w/mtp-example micro-os-plus-iii-aarch64/test/rpi-zero-2w/mtp-mine   # or mtp-smp, for a multi-core test
$EDITOR micro-os-plus-iii-aarch64/test/rpi-zero-2w/mtp-mine/*.cpp
cd tests && ./run.sh -c aarch64-rpi-zero-2w-cmake-gcc-debug mtp-mine
```

- One suite per source file, registered by the file itself:
  `mt::static_suite s{ "NN - Name", mtp_board::runner (), [] (mt::suite& ts) { ... } };`
  There is no list of suites in `main.cpp`; the runner discovers them (sorted by name).
- `main.cpp` is only `start ()`, the optional `release_cores ()`, and `run (argc, argv)`.
- Use `t.expect (...)`, not `t.require (...)`: the build has no exceptions, so a failed
  `require` aborts the whole run.
- Compare kernel results with `mtp::ok` or `mtp::code (EWOULDBLOCK)` and the other POSIX errors.
- A test that needs the real board ends its QEMU image with `return mtp_board::skip ("why");`
  under `#if !defined(HW_BUILD)`.
- A check that depends on one core pins its threads to core 0 (`th_cpu_affinity = 1u << 0`)
  when the test releases the other cores.
- Name the report path in the CTest case (the runners do it for `mtp-*`): `--output-file <path>`.

The board support's own README (`micro-os-plus-iii-aarch64/test/mtp/README.md`) lists the defines.
