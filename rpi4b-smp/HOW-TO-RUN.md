# Raspberry Pi 4 B SMP test workspace

This workspace was generated by `micro-os-scaffold` for the Raspberry Pi 4 B
(`aarch64-rpi4b`, 4 × Cortex-A72) with the µTest++ SMP test.

The test is `mtp-smp`. The harness in general is described in
`tests/ARCHITECTURE.md`/`.pdf`.

```text
micro-os-plus-iii-aarch64/test/rpi4b/mtp-smp/
├── main.cpp              start, release the other cores, run
├── smp_helpers.hpp       the helpers shared by the suites
├── suite-affinity.cpp    one suite, one file
├── suite-critical.cpp
├── suite-spinlock.cpp
├── suite-mutex.cpp
├── suite-scheduler.cpp
├── suite-cross-core.cpp
├── suite-queue-stress.cpp
├── suite-atomics.cpp
└── suite-speedup.cpp
```

It is generated from `micro-os-scaffold/templates/micro-test-plus/mtp-smp/`.
The suites register themselves; there is no suite list in `main.cpp`.

The workspace also carries the other starters:

- `mtp-args` — the semihosting `argc`/`argv` check (`00 - Arguments`, plus
  `00 - Cores` on this SMP board);
- `mtp-example` — the runtime + basics starter;
- `mtp-eth-net` — the GENET Ethernet test (hardware only);
- `smp_test4` — the StateOS stdc++ package adapted to µOS++ III (below).

## What it tests

| Suite | Checks |
|---|---|
| `00 - Cores` | all four cores joined the scheduler |
| `01 - Affinity` | a pinned thread stays on its core; affinity can be changed |
| `02 - Critical sections` | the kernel lock excludes all cores, masks/nests/restores this core's IRQs |
| `03 - Spinlocks` | no lost update from four cores; `try_lock` is refused while held |
| `04 - Mutexes` | contention from four cores, `timed_lock`, recursive mutexes, priority inheritance across cores |
| `05 - Scheduler` | preemption, equal-priority yielding, per-core sleeps, load spread |
| `06 - Cross-core sync` | semaphore ping-pong, message queue, event flags, a four-core barrier |
| `07 - Queue stress` | one producer per core into one bounded queue, nothing lost or duplicated |
| `08 - Atomic RMW` | `atomic_add ()` from every core (LDAXR/STLXR on the Pi) |
| `09 - Speed-up` | the same work on one core vs. all four |

## Run it

```bash
cd tests

./run.sh list          # all CTest cases

# Under QEMU (no board needed):
./run.sh mtp-smp
./run.sh mtp-args      # the argc/argv transport check

# On the board (JTAG/CMSIS-DAP probe attached):
./run.sh mtp-smp --hwd
./run.sh mtp-args --hwd
```

`./run.sh list` shows every case. The QEMU case is
`aarch64-rpi4b-mtp-smp-qemu`; the hardware case is
`aarch64-rpi4b-mtp-smp-hwd`.

## smp_test4: the StateOS stdc++ test

`smp_test4` runs the C++ standard-library parts a bare-metal toolchain does not
provide, on top of the StateOS `stdc++` layer adapted to µOS++:

```text
micro-os-plus-iii-aarch64/test/rpi4b/smp_test4/
├── main.cpp              start, release the cores, run
├── suite-thread.cpp      std::thread, jthread, ids, sleep, thread_local (TLS)
├── suite-promise.cpp     promise/future, wait_for status, shared_future
├── suite-future.cpp      packaged_task, async, set_value_at_thread_exit
├── suite-mutex.cpp       mutex, timed/recursive mutex, call_once
├── suite-sync.cpp        condition_variable, semaphores, latch, barrier
└── suite-chrono.cpp      steady_clock, system_clock, sleeps
```

The library is `third_party/stateos-stdc++/` (a relative link to the
repository's `third_party/stateos-stdc++/`). Its include directory is placed
before the toolchain's C++ headers, so `<bits/gthr-default.h>` is the µOS++
gthread layer and `<barrier>`, `<latch>`, `<semaphore>` are the versions built
on the kernel. See `third_party/stateos-stdc++/README.md` for the design and
the differences from the StateOS original.

```bash
./run.sh smp_test4          # under QEMU
./run.sh smp_test4 --hwd    # on the board
```

## Add a new SMP check

Add a `suite-<name>.cpp` file with its own static suite:

```cpp
#include <mtp_board.hpp>

mt::static_suite suite_my_check{
  "10 - My check", mtp_board::runner (), [] (mt::suite& ts) {
    ts.test ("all cores see the same value", [] (auto& t) {
      // ... check ...
    });
  }
};
```

The port's builder globs `*.cpp`, so no CMake file changes. The runner
discovers the new suite and runs it sorted by name.

## Moving or renaming this workspace

`tests/run.sh` and `tests/scripts/env.sh` derive the root from their own
location, so this folder can be renamed. A build tree moved with it is
detected from its `CMakeCache.txt` (`CMAKE_CACHEFILE_DIR` and
`CMAKE_HOME_DIRECTORY`) and rebuilt automatically; no manual `clean` is
needed. The tool paths in `tests/scripts/env.sh` remain absolute: on another
machine, re-scaffold or override them with `UOS_TOOL_<NAME>`.
